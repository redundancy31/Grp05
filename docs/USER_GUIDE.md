# User Guide

> **Current status:** The Python command reference below describes the retained legacy driver. Implemented Python-independent targets are `make`, `make test`, `make verify`, `make replay-test`, `make asm-test`, `make signals`, and `make readiness`. Native outputs go under `build/native/`. GNU Make was unavailable locally; direct GCC equivalents were exercised. Workflows without a native target remain Python-dependent and are listed in `docs/known_limitations.md`.

Run the driver from the repository root. In PowerShell use `python`; in MSYS2 UCRT64/Linux use `python3`. The examples below use `python3`. `scripts/project.py --help` and each subcommand's `--help` are authoritative when the parser changes. Dataset searches recognize `test20`, `dev_1M`, and `stress_full`; defaults are windows 3/5 for test20 and 30/60 for dev/stress.

## Common command effects

Build commands write executables and JSON source-hash metadata under `build/`. They do not create benchmark evidence. `clean-build` deletes generated files under `build/` only. Analysis/replay/profile commands write results; inspect their fresh run directory before sharing. Never point a result workflow at an existing directory or reuse an evidence path.

| `build-matrix` | `python3 scripts/project.py build-matrix` | GCC; builds normal variants and replay targets. Writes build artifacts/metadata only. |

| `replay-test` | `python3 scripts/project.py replay-test` | GCC; builds/runs replay-support C unit tests. Writes `build/tests/replay_support_tests.exe` on Windows or `build/tests/replay_support_tests` on Linux; no dataset or results evidence. Cross-platform subject to platform APIs. |

Example: `python3 scripts/project.py verify --dataset test20 --all-versions`. Prints per-version correctness status and writes/updates the correctness matrix under `results/laptop/`; dataset-gated, seconds to minutes. This is a result/evidence write; protect existing matrix evidence. No sudo/taskset. |
| `plot-signals` | `python3 scripts/project.py plot-signals [--dataset dev]` | Matching CSV of at least 2,500 rows with a qualifying signal region from rows 1,500-3,500; GNUplot optional. It may skip if no qualifying signal region. Do not run if those paths contain evidence you need to preserve. No sudo/taskset. |

No sudo expected. |

Cross-platform, read-existing/write-new file; no dataset/sudo/taskset. Annotation categories are heuristic and require human review. |

Requires built offline targets and the dataset; for test20 it also checks the official oracle. Runtime scales with input size. Cross-platform; it is not a timestamp-paced scheduling benchmark despite the help text. No sudo/taskset. |
| `compare-python` | `python3 scripts/project.py compare-python [--dataset stress_full] [--repeats N] [--platform-label LABEL] [--c-version ID] [--taskset-cpus CPU-LIST] [--short N] [--long N]` | GCC, dataset, official test20 oracle, and NumPy. Correctness-gates C/Python/NumPy first; writes raw/median/table/graph/manifest in a unique smoke directory for 1-4 repeats, or comparison directory for 5+. Cross-platform offline timing; not replay latency. `taskset` is optional on Pi; no sudo/LED. |

## Build and correctness sequence

For a new clone, use this order:

```sh
python3 scripts/project.py doctor
python3 scripts/project.py build-all
python3 scripts/project.py test --suite quick
python3 scripts/project.py verify --dataset test20 --all-versions
```

`build-all` creates all registered offline and replay targets. `test` may rebuild needed targets. `verify` checks the official expected output and the version matrix. A failure, skip, or missing dataset should be reported as such; do not translate a missing check into success.

## Evidence and timing notes

Each evidence-producing invocation should create a new timestamped run directory. Do not reuse a prior result path, change old raw files, or regenerate old result files. For benchmarks use at least five repeats, report the median, warm the program before measuring, and keep console/file output outside the timed loop. Use taskset and a recorded performance governor for controlled Pi measurements when supported. See [Reproducibility](REPRODUCIBILITY.md) for the full protocol and [Performance Methodology](performance_methodology.md) for timing definitions.

The default dataset names and file placement are covered in [Getting Started](GETTING_STARTED.md#dataset-placement). Result paths can depend on platform detection; inspect the printed path and manifest rather than assuming every host is Pi.
